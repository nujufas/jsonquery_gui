Query Engines

jaq was jsonquery's first query dialect, not its only one — JSON Pointer, JSONPath, and JMESPath now ship alongside it. This page surveys the wider JSON-query landscape — JSONPath variants, JSONata, JSON Pointer, JMESPath, and the JS-idiomatic tools (JSPath, Lodash, Underscore, raw JavaScript) — against a jsonquery_core::engine::QueryEngine trait built to hold more than one, records what was actually implemented from that survey, and recommends what to add next.

01Why more than jaq

Architecture §4 originally treated jaq's own ValT trait as the query integration point. That's since been generalized: QueryEngine now lives in the engine-agnostic core (crates/core/src/engine.rs), and jaq (crates/query/src/jq.rs's JaqEngine) is its first implementor, not a permanent special case — see Decision 2 for the original jq-vs-alternatives call. The prompt for this survey was a look at jsonquerytool.com's own transform-step picker, which lists ten-odd dialects side by side — this page asks which of those (and a few it misses, like JMESPath) are actually worth building a second, third, or fourth QueryEngine for.

02What's shipped

The survey's own "ship first" order (below) is exactly what landed: JSON Pointer (crates/query/src/json_pointer.rs, JsonPointerEngine, RFC 6901 via serde_json::Value::pointer), JSONPath (crates/query/src/jsonpath.rs, JsonPathEngine, via jsonpath-rust), and JMESPath (crates/query/src/jmespath_engine.rs, JmesPathEngine, via the jmespath crate) all now implement QueryEngine alongside JaqEngine.

A new jsonquery_query::Kind enum (crates/query/src/lib.rs) ties each dialect's id to its engine and adds Kind::detect(query_text) — best-effort auto-selection from the query's own syntax (a leading / means JSON Pointer, a leading $ means JSONPath, a few JMESPath-only substrings like [?/backtick literals/&&/|| mean JMESPath, everything else — including jq's own leading . — defaults to jq). The query bar gained four small selectable-label buttons, top right, one per dialect: none selected (the default) means "auto," clicking one pins that engine explicitly, and the status bar reports which engine actually ran — e.g. jq · auto vs. a manually-picked JMESPath — so a result is never ambiguous about which dialect produced it.

⚠
Pitfall: JMESPath + arbitrary_precisionThis workspace's serde_json runs with the arbitrary_precision feature; jmespath's generic Serialize-based ToJmespath impl doesn't understand the private sentinel that feature emits for numbers, so feeding it a &Value the "obvious" way silently turned every number into an unrelated object and broke numeric filters (age > `30` matched nothing). Fixed in jmespath_engine.rs by converting Value → jmespath::Variable by hand, matching on Value's variants directly instead of round-tripping through Serialize. Worth checking for again if a future engine also bridges through a generic Serialize impl rather than matching Value natively.

jsonquerylang.org's own DSL		 none — JS/TS + Python reference implementations only ISC — No Rust port exists anywhere. It's deliberately small (~4.2 kB minified, pipe syntax, ~50 built-ins) — closer in scope to how jaq itself was integrated than to adding a dependency. Future — from scratch
JS-idiomatic tools
JSPath, Lodash, Underscore, raw JavaScript		 boa_engine — a JS engine, not a query-language crate Unlicense OR MIT ~4.7M downloads None of these four have a Rust port individually — they're JS utility libraries, not declarative query languages. boa is the only pure-Rust JS engine of note, so it's the one way to support all four at once (load lodash/underscore's own source as a JS "prelude") without breaking the single dependency-free-binary goal (Decision 1) the way a QuickJS/V8 binding would. Future — bigger lift
Recommendation (shipped 2026-09-05): JSON Pointer, jsonpath-rust, and jmespath are all implemented — see What's shipped. JSONata, jsonquerylang.org's own DSL, and a boa-backed JS/Lodash mode remain separately-scoped follow-ups — an immature dependency, a from-scratch implementation, and a full embedded scripting engine, respectively — not quick wins alongside the first three.
ℹ
"JSON to XML" isn't a query enginejsonquerytool.com's picker also lists xml2js — a format converter, not a query language, and unrelated to QueryEngine. It maps onto the roadmap's already-planned Decision 5 "CSV / NDJSON export" item as another output format, not a new dialect. quick-xml or serde-xml-rs would be the Rust tool for that, if it's ever wanted.

Research notes & sources

Checked 2026-09-05 via crates.io's API and each project's GitHub/homepage. Crate versions and maintenance status move — re-verify before implementation, the way Decisions & Roadmap's own sources note already asks for.

  • jsonquerytool.com — the transform-step engine picker that prompted this survey.
  • jsonquerylang/jsonquery — the jsonquerylang.org DSL: syntax, ISC license, JS/TS + Python reference implementations, no Rust port.
  • jsonata.org and Stedi/jsonata-rs — JSONata language and its alpha-stage Rust port.
  • jsonpath-rust and serde_json_path (crates.io) — RFC 9535 JSONPath implementations.
  • RFC 9535 — JSONPath: Query Expressions for JSON.
  • jmespath and jmespath_community (crates.io) — JMESPath implementations.
  • jql-runner (crates.io) — the Rust-native JSON Query Language tool.
  • boa-dev/boa — pure-Rust JavaScript engine, evaluated as the route to JSPath/Lodash/Underscore/raw-JS support.
  • RFC 6901 (JSON Pointer) — satisfied already by serde_json::Value::pointer(), no separate crate.
