02File ingest & memory-mapping

The file is opened with memmap2 rather than read into a Vec<u8>. That gives three things for free: opening a 5 GB file is instant (no upfront copy), the OS page cache does the paging work we'd otherwise hand-roll, and unused pages never occupy heap memory. The mapped bytes (&[u8]) are the single source of truth for the rest of the pipeline — the index and the query engine both read into this slice rather than copying out of it wherever possible.

ℹ
Small-file fallbackBelow a size threshold (see Decision 3), the same mmap path is used, but the indexing stage below is skipped in favor of a direct in-memory parse — see the Phase 1 note under Roadmap.

03Indexing layer — checkpoints over a lazy reader

This is the piece that makes huge files feel small, and it's the part of the original draft that changed the most under research. The original plan was to hand-roll a full per-node "tape" scanner. That's no longer necessary: sonic-rs, a SIMD-accelerated JSON library, already provides exactly the low-level primitive this layer needs — for free, and battle-tested.

✓
Research findingsonic-rs's get()/get_unchecked() return a LazyValue — a wrapper around a raw, unparsed JSON slice, located by SIMD-accelerated skipping. Critically, these APIs take a plain immutable &str/&[u8] — no mutable copy required — so they work directly against bytes borrowed from a memory-mapped file. It also exposes to_array_iter() / to_object_iter_unchecked() for sequential lazy iteration without materializing values. Apache-2.0 licensed.

What sonic-rs does not give us is guaranteed O(1) random access into an arbitrary child — get() skips forward from the start of a container using SIMD, which is very fast per byte but still О(k) in the number of preceding elements. For a 50-million-element array, jumping straight to element #40,000,000 (e.g. dragging the results scrollbar) would re-skip 40 million elements every time unless something remembers where things are.

The design: a sparse checkpoint table, not a full tape

So the indexing layer isn't a parser — it's a thin bookkeeping pass on top of sonic-rs's reader. One lightweight forward pass over each container records a byte offset every N children (tunable, e.g. every 4,096th array element or object key) instead of every single one:

Checkpoint tablearray of len 50,000,000offset[0], offset[4096], offset[8192], …
→
Resolve child #4,213,0001. checkpoint = 4,213,000 / 4096 → O(1)2. sonic-rs skip remainder (≤4096) → fast

Memory cost is ~1/4096th of a full per-node tape; worst-case lookup cost is bounded by the checkpoint interval, not by document size.

This cleanly splits by access pattern:

  • Indexed access — .key, .[i], .[a:b], and the tree widget resolving a visible row — use the checkpoint table for bounded-cost point/slice lookup.
  • Sequential access — .[], keys, to_entries, and any full-scan filter — use sonic-rs's lazy iterators directly. These are inherently O(n) by nature of visiting every child, not a limitation of our design, and they still never materialize more than one child at a time.

NDJSON and concatenated JSON

A lot of real "large JSON files" are actually newline-delimited JSON — one value per line, common for log exports and data dumps — rather than a single giant document. The indexer treats the file as one or more top-level values from the start (each gets its own checkpoint-indexed pass) instead of assuming exactly one root, so an NDJSON file works the same day as a single huge document, with no separate "format" to support. Confirm this matches your use case — see Decision 3.

Parallel first pass (optional, later)

For the common "one giant top-level array of records" shape, the checkpoint-building pass can be chunked across threads with rayon: cheaply find approximate element boundaries, checkpoint each chunk in parallel, then merge. A Phase 2 optimization, not required for correctness.

⚠
Build/portability notesonic-rs's fast paths target x86_64 and aarch64 and lean on SIMD feature flags; other architectures fall back to a slower path automatically. Distributed binaries should target a safe explicit feature baseline (or runtime CPU-feature dispatch) rather than target-cpu=native, which only helps builds compiled on the exact machine that runs them. Tracked in Open risks.

04Query engine — embedding jaq

jaq is a jq clone written in Rust and usable as a library, not just a CLI. Embedding it means the query language, its parser, and its evaluator arrive largely for free and match syntax users already know — see Decision 2 for the full comparison against the alternatives.

The integration point: ValT

jaq-core is generic over the value type via a trait, ValT — implement it for a custom type and jaq's evaluator runs over that type instead of a built-in Value. Reading the trait closely changes the earlier "unvalidated" risk into a concrete design:

  • Structural methods like key_values(self) -> BoxIter<'static, …> and values(self) -> Box<dyn Iterator<…>> carry a 'static bound — but that only forbids borrowing a stack lifetime. An owned handle carrying a cheap Arc<Mmap> clone satisfies 'static just fine, and Box<dyn Iterator> is a real pull-based lazy iterator regardless of boxing — it doesn't force eager collection.
  • So the natural shape is: enum Val { Lazy { mmap: Arc<Mmap>, range: ByteRange, checkpoints: Arc<Index> }, Owned(serde_json::Value) }. A Lazy value's index/range/key_values/values resolve children via the checkpoint table from §3 and wrap each child as another cheap Lazy handle — no recursive parsing until a leaf is actually read (as_bool, into_string, arithmetic, …).
  • from_map/from_num and anything a query constructs (object/array literals, arithmetic results, string interpolation) naturally falls back to the Owned variant — those values were never backed by source bytes in the first place, so there's nothing to keep lazy.

This is still a design sketch, not a proven implementation — see the spike in Open risks — but it's now a "confirm it performs" question rather than a "figure out if it's possible" question.

Two free wins that came out of this research

Exact number round-tripping

jq's identity filter is required (since jq 1.7) to preserve a number's original literal text when it isn't arithmetically touched — jaq satisfies this via serde_json's arbitrary_precision feature. A 64-bit snowflake-style ID or a Postgres bigint survives a select(...) or .foo query byte-for-byte, instead of silently rounding through an f64 the way naive JSON tooling does. This falls out of the architecture already, at no extra cost.

Short-circuiting queries

jaq's evaluator is generator-based, like jq itself: every filter yields a lazy stream of outputs. first(...), limit(n; …), and slicing stop pulling as soon as they have enough — jaq's own changelog specifically tracks correctness fixes to this exact behavior. Combined with §7 below, "give me the first 20 matches" against a 50-million-element array can genuinely stop early rather than quietly running to completion in the background.

05Concurrency model

The UI thread never touches the file, the index, or the query engine directly — it sends commands and receives messages over a crossbeam-channel pair.

UI threadegui/eframe
Open(path) / Query(text, gen) / Cancel
→
←
Progress / Indexed / Rows(gen) / Error
Worker threadingest · index · query

Two things fall out of this cleanly:

  • The window never freezes. Loading a 5 GB file or running an expensive query happens entirely off-thread; the UI keeps redrawing (a spinner, byte-scanned progress) using the last message received.
  • Stale work is cheap to discard. Every query carries a monotonically increasing generation number. If the user edits the query field and re-submits before the previous run finishes, the worker is told to abort (checked at safe points during indexing/evaluation), and the UI ignores any late results tagged with an old generation.

06GUI layer & the virtualized tree widget

Built on egui/eframe (see Decision 1 for why). The window is three panels: a multiline query bar pinned to the top, and two instances of the same custom widget below it — the source tree (the loaded document) and the results tree (the last query's output).

How the virtualization actually works

Expand/collapse state is not stored on the tree itself — it lives in a side map keyed by node path (HashMap<NodePath, bool>). Every frame, the widget:

  1. Reads the current scroll offset and viewport height from egui.
  2. Computes which row indices are visible, given a fixed row height (visible_start = offset / row_height, etc.) — an arithmetic step, not a walk.
  3. Resolves only those rows against the index — following expand state to skip collapsed subtrees — and draws them.
  4. Reserves the correct total scroll height up front (row count × row height) so the scrollbar is accurate without ever visiting off-screen rows.

The cost of one frame is therefore bounded by viewport height, not document size — scrolling a 50-row window feels identical whether the document has 500 nodes or 500 million.

⚠
Second spikeThis is a standard technique, but it needs to be prototyped against a real multi-GB synthetic file (both "deeply nested" and "one huge flat array" shapes) before the rest of the GUI is built on top of it. See Open risks.

07Results handling

Query results need the same care as the source document — .[] | select(...) over a large array can itself produce millions of rows. The results tree reuses the exact virtualized widget from above, but the data behind it is populated differently:

  • Streamed, not collected. The query executor pushes result items to the UI incrementally as jaq produces them, rather than collecting the full output before returning anything — the results pane starts filling in immediately. This is a direct consequence of jaq's generator-based evaluation (§4) — there's no "wait for the whole result set" step to bypass.
  • Bounded live preview. The in-memory/rendered preview caps at a configurable count (e.g. the first 50k items); the status bar shows "50,000+ shown, query still running / N total" rather than trying to hold an unbounded result set in memory.
  • Full export bypasses the cap. "Save results to file" re-runs the query in a streaming write mode straight to disk, so exporting 10 million matched rows never requires materializing them all at once in RAM.

09Proposed workspace layout

A Cargo workspace with the lazy-index logic, the query adapter, and the GUI kept as separate crates — mainly so the index/query core can be unit-tested and benchmarked (via criterion) without pulling in a GUI toolkit.

jsonquery/
├── Cargo.toml                # workspace
├── crates/
│   ├── core/                 # mmap ingest, sonic-rs-backed checkpoint index
│   ├── query/                # jaq ValT integration — Lazy/Owned Val adapter
│   └── app/                  # eframe app: panels, virtualized tree widget, worker thread
├── docs/                     # this site
└── benches/                  # criterion benchmarks against synthetic large files
