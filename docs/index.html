Architecture proposal · Draft

jsonquery

A native desktop tool for querying and browsing large JSON files — fast to open, fast to scroll, fast to query. This is the architecture proposal: read it, then use the Decisions page to lock in the choices that shape everything else.

01The problem

Poking at a large JSON file today means picking one of three bad trade-offs: the jq CLI is fast and expressive but has no visual browser, so you're re-running commands blind; a browser-based JSON viewer looks great on a 2 MB file and then locks the tab on a 2 GB one; and general editors like VS Code will open large files but treat them as text, not structure — no collapsible tree, no query.

There isn't a tool that combines "open anything, however large, instantly" with "query it like jq, and see the result as a tree you can actually scroll." That's the gap this project fills.

02Goals

  • Open large files without flinching. Drag-and-drop or file-picker, targeting files from a few KB up to multiple GB, without freezing the UI while it loads.
  • Query like jq. A multiline query field at the top of the window, running a jq-compatible query language against the loaded document.
  • Scroll like it's a text file, not a spreadsheet of doom. Both the source tree and the results pane stay smooth — constant frame time — regardless of how many nodes exist off-screen.
  • Stay responsive. Loading, indexing, and querying happen off the UI thread; a slow query can be cancelled by simply starting a new one.
  • Ship as one binary. No runtime install, no bundled browser engine — a native window that opens fast.

03Non-goals v1

Explicitly out of scope for the first version, to keep the initial build tight:

  • Editing JSON in place (this is a viewer + query tool, not an editor).
  • Schema validation / linting.
  • Multiple files open at once, tabs, or session management.
  • Remote or cloud-hosted files — local files only.
  • Other formats (YAML, CSV) — pure JSON in. NDJSON (one JSON value per line) is treated as a shape of JSON input, not a separate format — see Architecture §3 — and NDJSON export of results may show up later too.

04Guiding principles

  • Never block the UI thread. File I/O, parsing/indexing, and query execution all happen on a worker thread; the GUI only ever reads results handed back over a channel.
  • Never materialize what you don't need to render. If a row isn't visible, its value shouldn't be fully parsed, copied, or allocated yet.
  • Reuse a real query engine, don't invent one. jq syntax is already muscle memory for the target user — see Decision 2.
  • Prove the risky parts early. The two things most likely to blow up the plan — lazy querying and virtualized scrolling at real scale — get prototyped before the rest is built around them. See Open risks.
