Open questions

Decisions & Roadmap

Five choices shape the rest of the build. Each one below has a recommendation baked in — read the trade-offs, then either confirm the recommendation or swap it for something else before any code gets written.

ℹ
Every decision defaults to its recommended option in the roadmap at the bottom of this page. If you don't override anything, that's the plan that gets built.

1. GUI framework

What draws the window, the panels, and — critically — the virtualized tree?

egui / eframe

Recommended

Pure-Rust immediate-mode GUI, single native binary.

Pros
  • No webview or extra runtime — one binary, fast startup
  • Immediate mode makes custom row virtualization direct to implement
  • Native drag-and-drop + file dialogs with little glue
Cons
  • Default styling is utilitarian; polish takes manual work
  • Rich text / text editing widgets are less mature than a browser's

Tauri

Alternative

Rust backend, HTML/CSS/JS frontend in a system webview.

Pros
  • Mature virtualized-list libraries (e.g. TanStack Virtual) for free
  • CSS styling gives the fastest path to a polished look
Cons
  • Webview dependency (WebView2 / WebKitGTK) — not a single self-contained binary
  • Rust ⇄ JS IPC boundary — large result sets must be paginated across it
  • Two languages/toolchains instead of one

iced

Alternative

Pure-Rust, Elm-architecture retained-mode GUI.

Pros
  • Explicit state/update model, predictable for complex forms
  • Also a single native binary
Cons
  • Lazy/virtualized-list support less proven for this scale of data
  • More boilerplate to build a fully custom widget

gpui

Higher risk

Zed's GPU-accelerated UI framework.

Pros
  • Proven at huge-file scale — it's what Zed's editor runs on
  • GPU-accelerated rendering, very fast
Cons
  • Young outside Zed itself, thinner docs and community
  • Steepest learning curve of the four
Recommendation: egui/eframe. It's the only option that's both a single dependency-free binary and gives direct control over the virtualization strategy the whole app depends on — no fighting a framework's built-in list widget to get there.

2. Query language

What goes in the multiline query field, and what runs it?

OptionProsCons
Embed jaq Recommended
jq-compatible, pure Rust		 Users likely already know jq syntax; filters, pipes, and functions arrive without designing a language. Generator-based evaluation short-circuits first/limit; preserves exact number literals via serde_json's arbitrary_precision — see Architecture §4. jq's grammar is genuinely large — needs an explicit "supported subset" for v1; the lazy ValT adapter has a credible design (Architecture §4) but is still unproven at scale.
jq-rs (FFI)
binds the real libjq C library		 Perfect behavioral compatibility with actual jq — zero language-subset risk, since it is jq. Requires linking libjq (and its oniguruma dependency) at build time — directly conflicts with Decision 1's "single self-contained Rust binary" goal, and complicates cross-compilation/packaging. Unsafe FFI surface to maintain.
serde_json_path
JSONPath, RFC 9535		 Implements the actual IETF JSONPath standard, actively maintained, MIT-licensed, smallest integration surface of any option here. Still a path-selector language — no pipelines, transforms, or aggregation. Doesn't serve the "useful for the future" goal as well as a real query language.
Custom DSL Full control — can be designed exactly around the lazy index. Reinvents a query language from scratch; ongoing design/doc burden; zero user familiarity on day one.
Recommendation: embed jaq. It's the highest-leverage option — a real, maintained jq implementation in Rust — and syntax familiarity means zero onboarding for anyone who's used jq before. jq-rs was seriously considered (it removes all language-compatibility risk) but rejected specifically because it breaks the single-binary goal from Decision 1; jaq keeps everything in one dependency-free Rust binary. The lazy-integration question is real but scoped as an explicit early spike, not a blocker to deciding the language itself.

3. Scale target

How large is "large," concretely? This determines how much of Architecture §2–3 is required for v1 versus deferred.

TargetWhat it requires
Up to ~200 MBComfortable fully in-memory — Phase 1 alone is sufficient, no checkpoint index needed.
A few GB RecommendedNeeds the mmap + sonic-rs-backed checkpoint index from Architecture §3 — Phase 2.
10 GB+ / arbitraryNeeds streaming query execution, not just streaming parse — results themselves may not fit in RAM either. Bigger lift; not v1.
Recommendation: design for "a few GB" as the v1 ceiling (Phase 2 of the roadmap below), while keeping the index/adapter layer generic enough to push further later. Phase 1 ships the in-memory path first, on purpose — it validates the GUI and query integration on small files before the harder scale work begins.
⚠
Also confirm: input shapeA lot of real-world "large JSON" is actually NDJSON — one JSON value per line, common for log exports and data dumps — rather than a single giant document. Architecture §3 now treats the file as one-or-more top-level values from the start so NDJSON works day one, not as a deferred format. Flag if this doesn't match what you'll actually be opening.

4. Editing capability

Viewer + query tool, or also an in-place JSON editor?

Read-only

Recommended

View and query only — matches every goal on the Overview page.

Editable

Later

Adds structural editing, undo/redo, and safe write-back to a memory-mapped file — a different, larger project.

Recommendation: read-only for v1 (already reflected in Non-goals). Editing is orthogonal to "query large files fast" and would pull in an entirely separate set of hard problems (safe writes to a mmap'd file, undo history). Revisit only after the core tool is solid.

5. Result export

Once a query has run, how does the output leave the app?

Clipboard only

Minimal

Copy selected node or copy-all (bounded by the live preview cap).

Copy + save to file

Recommended

Adds "save full results to file," streamed straight to disk via a re-run of the query — never limited by the live preview cap.

+ CSV / NDJSON

Phase 3

Format conversion on export — genuinely useful, but not required to validate the core tool.

Recommendation: ship "copy + save to file" in v1 (see Architecture §7 Results handling for how streamed export avoids materializing huge result sets in memory); defer format conversion to Phase 3.

⚠Open risks & early spikes

Assumptions the architecture leans on. The two most load-bearing now have a concrete design behind them (see Architecture §3–4), but "designed" isn't "proven" — each still gets a throwaway prototype before the real build depends on it.

  • jaq's ValT × the Lazy/Owned Val design. Architecture §4 now has a concrete adapter sketch (an Arc<Mmap>-backed lazy handle satisfying ValT's 'static bound). The remaining question is narrower than before: does it actually compile cleanly against the trait, and does it perform — confirm on a synthetic multi-GB array before the rest of the query path assumes it works.
  • egui virtualized scrolling at real scale. Prototype scrolling a synthetic 5–10 GB file in both shapes that matter — deeply nested, and one enormous flat array — and measure frame time before the rest of the GUI is built on the assumption it holds up.
  • Checkpoint interval tuning. A single array with tens of millions of elements stresses the checkpoint table from Architecture §3 — confirm a checkpoint interval (e.g. every 4,096th element) gives acceptably bounded lookup cost in practice, and that memory overhead stays a small fraction of file size.
  • SIMD build portability. If sonic-rs anchors the indexing layer, decide the build strategy — safe explicit target-features vs. runtime CPU dispatch — so a distributed binary doesn't crash on an older or non-x86_64/aarch64 machine. See Architecture §3.
  • Malformed / truncated input. Decide how much recovery the indexer attempts versus failing fast with a precise byte offset in the error.

→Roadmap

Three phases. Each one ships something usable — Phase 1 alone is already a working tool for small-to-medium files.

1
Phase 1 · MVP

In-memory, small-to-medium files

Prove the GUI shell and the query integration before taking on scale.

  • Full in-memory parse (serde_json, swap for simd-json if profiling justifies it)
  • jaq embedded directly against owned Values — no adapter needed yet
  • egui app shell: multiline query bar, two virtualized tree panels wired to the in-memory value
  • Drag-and-drop and file-picker open
  • Status bar: parse time, query time, node/result counts
  • Cancellation for slow queries via the generation-counter pattern
2
Phase 2 · Scale

Multi-GB files without freezing

Everything in Architecture §2–3, built on whatever the spikes in Open risks actually confirm.

  • mmap ingest replaces full-file reads
  • sonic-rs-backed sparse checkpoint index (Architecture §3) with lazy scalar resolution
  • Ship the Lazy/Owned ValT adapter for jaq (Architecture §4), confirmed by its spike
  • Background indexing with progress reporting
  • Streamed/incremental result materialization with the bounded live-preview cap
  • Cancellation wired through indexing and query execution, not just query
3
Phase 3 · Polish

Everyday-tool ergonomics

Includes one differentiator that falls directly out of the indexing design: because the checkpoint index already knows every key and array shape without materializing values, path/key autocomplete in the query field is nearly free — most jq tools can't offer this without a full parse.

  • Query history and saved queries
  • Syntax highlighting in the query field
  • Schema-aware autocomplete — suggest keys/paths as you type, sourced straight from the checkpoint index
  • CSV / NDJSON export alongside raw save-to-file
  • Recent files list
  • Light/dark theme
  • Keyboard-driven tree navigation

Research notes & sources
